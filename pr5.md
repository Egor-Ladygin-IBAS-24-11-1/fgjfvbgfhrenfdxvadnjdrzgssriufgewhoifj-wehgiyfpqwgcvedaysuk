# ПР №5. GPG, подпись коммитов и безвозвратное удаление

## 1. GPG-ключевая пара

- Key-ID: `5BDEF3B50D040EE5`
- Тип: RSA 4096 бит
- Email: `minecraft01082002@gmail.com`
- Размер публичного ключа: 30 строк (включая блок BEGIN PGP PUBLIC KEY BLOCK)

Что означает флаг --armor: Флаг `--armor` (ASCII Armor) преобразует бинарные данные GPG в текстовое представление (Base64), что позволяет передавать ключи и подписи по электронной почте, в текстовых файлах или в системах контроля версий без искажения данных. Без этого флага GPG создаёт бинарные файлы.

Можно ли прочитать исходные данные из зашифрованного файла: Нет, зашифрованный файл содержит данные в формате Base64, которые невозможно прочитать без расшифровки. Это бинарные данные, представленные в текстовом виде.

Что произойдёт если ввести неверный пароль при расшифровке: GPG выдаст ошибку `gpg: decryption failed: Bad session key` или аналогичную, после чего расшифровка не выполнится, и исходные данные не будут получены.

Почему нельзя расшифровать файл зашифрованный для другого пользователя: Шифрование выполняется с использованием **публичного ключа** получателя. Расшифровать данные можно только **секретным ключом**, соответствующим тому публичному ключу, на который выполнялось шифрование. У другого пользователя нет соответствующего секретного ключа, поэтому расшифровка невозможна.

Вывод gpg --verify после изменения файла (BAD signature):

gpg: Подпись сделана Чт 14 мая 2026 10:36:34 +05
gpg: ключом RSA с идентификатором 51A121A4E3DEA4164E6C9E8A5BDEF3B50D040EE5
gpg: ПЛОХАЯ подпись пользователя "Egor-Ladygin-IBAS-24-11-1 (amogus) minecraft01082002@gmail.com" [абсолютное]


Почему подпись перестала быть действительной после изменения файла: Цифровая подпись вычисляется на основе хэша (отпечатка) содержимого файла. При любом изменении файла — даже одном символе — хэш меняется, и подпись перестаёт соответствовать содержимому.

Что именно проверяет gpg --verify: Проверяет две вещи: 1) что подпись была создана указанным приватным ключом (подлинность отправителя); 2) что содержимое файла не изменилось с момента подписания (целостность данных). Это достигается за счёт проверки хэша файла по подписи.

Это даёт дополнительный уровень безопасности и независимости от внешнего сервиса.

## 5. rm vs shred

| Операция | Что происходит с данными на диске | Можно восстановить? |
|----------|----------------------------------|---------------------|
| rm       | Удаляется только запись в метаданных (inode), данные остаются на диске до перезаписи | Да, с помощью специализированных утилит (PhotoRec, TestDisk), пока блоки не перезаписаны |
| shred    | Содержимое блоков многократно перезаписывается случайными данными (по умолчанию 3 прохода) | Нет, после перезаписи оригинальные данные восстановить невозможно |

Сценарий когда нужно затирать свободное место: При утилизации жёсткого диска перед продажей или передачей другому лицу; при удалении файлов с конфиденциальной информацией (пароли, ключи, финансовая отчётность, медицинские данные) на неперешифрованных дисках; при соблюдении стандартов безопасности (например, PCI DSS, HIPAA, GDPR), требующих гарантированного безвозвратного удаления данных.

## Контролные вопросы:

68. Разница между шифрованием и подписью
Шифрование — скрывает содержимое (читает только владелец приватного ключа). Подпись — подтверждает авторство и целостность (не скрывает данные). Да, можно одновременно зашифровать и подписать: gpg --sign --encrypt

70. Почему публичный ключ можно всем, а приватный — никому?
Публичный ключ только шифрует и проверяет подписи. Приватный — расшифровывает и подписывает. Потеря приватного = потеря доступа к своим данным.

70. Что будет с зашифрованными данными при потере приватного ключа?
Данные будут потеряны навсегда. Расшифровать без приватного ключа невозможно (кроме брутфорса, который бесполезен при хорошей длине ключа).

72. Можно подделать Verified коммит без приватного ключа?
Нет. GitHub проверяет криптографическую подпись. Без приватного ключа подпись создать невозможно.

72. Почему shred плох для SSD? Что вместо него?
SSD использует wear-leveling и кэш — команды перезаписи уходят не на те же физические ячейки. Вместо shred использовать аппаратное шифрование диска + удаление ключа, или команду blkdiscard, или утилиту от производителя SSD.

74. Коллега не прав: форматирование безопасно?
Нет. Обычное форматирование удаляет только таблицу файлов. Данные восстанавливаются утилитами (PhotoRec, TestDisk). Безопасно только перезапись (или шифрование + удаление ключа).

74. Detach-sign vs обычная подпись
Обычная подпись (--sign) — встраивает подпись в файл. Detach-sign — создаёт отдельный .sig файл, оставляя исходный нетронутым. Удобно для дистрибутивов ISO и исполняемых файлов.
